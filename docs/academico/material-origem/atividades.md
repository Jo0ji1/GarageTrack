Atividade 1

PROJETO FINAL - ETAPA 1

Objetivo:

Esta atividade tem como propósito orientar o aluno nos primeiros passos do projeto final da disciplina, promovendo uma compreensão inicial e estruturada do desenvolvimento de aplicativos para dispositivos móveis.

Resumo do Projeto:

O projeto final consistirá na criação de um aplicativo inovador, abordando temas relevantes à disciplina. Lembrando que o aplicativo deve utilizar as seguintes tecnologias: Banco de dados, mídia (vídeo, aúdio, câmera, etc) e GPS.

O aluno deve escolher um contexto de aplicação, considerando desafios e oportunidades para aplicar as tecnologias mencionadas.



Modelagem de Engenharia de Software:

1. Levantamento de Requisitos: Identificar funcionalidades essenciais e requisitos do sistema.

2. Diagrama de Casos de Uso: Mapear as interações entre usuários e o sistema.

3. Diagrama de Classes: Definir a estrutura de classes e relações no sistema.

4. Prototipagem Rápida: Utilizar ferramentas como Figma para criar protótipos iniciais.

 

Rascunho das Telas Principais (Figma):

Utilize o Figma para esboçar as telas-chave do seu aplicativo, considerando a experiência do usuário e a navegabilidade. Certifique-se de representar as transições entre telas.

 

Lembre-se: O trabalho é individual ou dupla, mas colaboração na troca de ideias é incentivada. Submeta seu documento e protótipos até a data estipulada.






Atividade 2

Atividade em Sala – Proposta Rápida de Aplicativo Móvel

Disciplina: Programação para Dispositivos Móveis
Professor: Dr. Raul Paradeda
Modalidade: Individual ou Dupla
Prazo de desenvolvimento do app: 20 dias

1. Objetivo da Atividade

Definir, de forma rápida e objetiva, a ideia de um aplicativo móvel que será desenvolvido ao longo dos próximos 20 dias.

A proposta deve ser construída com apoio de ferramentas de IA, mas precisa demonstrar entendimento claro do problema, da solução e da viabilidade técnica.

2. Entrega Esperada (Durante a Aula)

Cada aluno/dupla deverá entregar um documento simples contendo a proposta do aplicativo.

Importante:

O foco é objetividade, não quantidade de texto
Respostas vagas ou genéricas serão penalizadas
A proposta deve ser realista para implementação em 20 dias
3. Estrutura do Documento (Obrigatória)

3.1 Identificação

Nome(s)
Nome do aplicativo
3.2 Problema (máx. 5 linhas)

Descreva claramente qual problema o aplicativo resolve.

Evite: ideias genéricas como “facilitar tarefas do dia a dia”.

3.3 Solução Proposta (máx. 5 linhas)

Explique como o aplicativo resolve o problema.

3.4 Público-Alvo

Quem usará o aplicativo?

3.5 Funcionalidades Principais (3 a 5 no máximo)

Liste apenas as funcionalidades essenciais.

Exemplo:

Cadastro de usuário
Registro de atividade
Visualização de histórico
3.6 Fluxo Básico (passo a passo simples)

Descreva como o usuário usa o app.

Exemplo:

Abre o app
Realiza login
Executa ação principal
Visualiza resultado
3.7 Wireframe Simples

Desenho (manual ou digital) de 1 a 3 telas principais.

Pode ser:

Papel (foto)
PowerPoint
Figma
Qualquer ferramenta simples
Não é necessário design detalhado.

3.8 Tecnologias (nível básico)

Indique o que pretendem usar:

Linguagem (Kotlin, Java, etc.)
Armazenamento (SQLite, Firebase, etc.)
3.9 Viabilidade (item crítico)

Explique em até 3 linhas por que esse app pode ser feito em 20 dias.

4. Uso de Inteligência Artificial

O uso de IA é permitido e incentivado, porém:

Vocês devem entender o que estão propondo
Devem ser capazes de explicar oralmente a proposta
Não será aceito conteúdo incoerente ou desconectado da realidade técnica
6. Observação Final

Esta atividade não é o projeto final da disciplina.
O objetivo aqui é validar rapidamente uma ideia simples, funcional e implementável.

Aplicativos pequenos, bem definidos e executáveis serão melhor avaliados do que ideias grandes e inviáveis.

7. Nível Mínimo de Complexidade (Obrigatório)

O aplicativo proposto deve ir além de implementações básicas.

Não serão aceitas propostas que consistam apenas em:

Lista de tarefas (To-do list simples)
Cadastro simples de usuários ou itens
Aplicações puramente estáticas (sem lógica relevante)
CRUD básico sem diferencial funcional
8.1 Requisito de Complexidade

O aplicativo deve conter pelo menos 2 dos itens abaixo:

A. Lógica de Negócio Relevante

Regras de decisão (ex: recomendações, validações, cálculos)
Processamento de dados do usuário
Comportamento dinâmico baseado em entradas
B. Interação com Recursos do Dispositivo

GPS / localização
Câmera
Sensores
Notificações
C. Persistência de Dados com Estrutura

Banco de dados com mais de uma entidade relacionada
Histórico de ações do usuário
Organização de dados com significado (não apenas armazenamento simples)
D. Experiência de Usuário com Fluxo Não-Trivial

Mais de um fluxo principal (ex: cadastro + uso + acompanhamento)
Navegação estruturada entre múltiplas telas com propósito claro
E. Integração Externa (nível básico)

Uso de API simples (ex: clima, mapas, etc.)
Consumo de dados externos
8.2 Regra de Ouro

O projeto deve responder à seguinte pergunta:

“Existe alguma lógica ou comportamento no sistema que exige raciocínio de programação, e não apenas interface?”

Se a resposta for “não”, o projeto é simples demais.

8.3 Exemplos para Calibração

Aceitáveis (nível adequado):

App de controle financeiro com categorização automática e relatórios
App de rotina de estudos com recomendações baseadas em desempenho
App de monitoramento de hábitos com notificações inteligentes
App que usa localização para sugerir ações/contextos
Não aceitáveis (simples demais):

Lista de tarefas sem lógica adicional
Cadastro de produtos sem processamento
Agenda estática
App apenas informativo
Não aceitáveis (complexos demais para 20 dias):

Rede social completa
App estilo Uber/iFood
Sistema com múltiplos perfis complexos e backend robusto
8.4 Observação Importante

A avaliação não será baseada na quantidade de funcionalidades, mas na qualidade da lógica implementada.

Um app com poucas funcionalidades, mas com comportamento inteligente e bem definido, será melhor avaliado do que um app com muitas telas e pouca lógica.
